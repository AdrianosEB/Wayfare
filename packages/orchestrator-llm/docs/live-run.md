## Finding: four agents cannot use the LLM path at all

This run did what it was built to do — it found a second bug of exactly the same class as
`top_p: -1`, and one that no stub test could have caught.

**Six of ten agents worked.** `intake`, `persona`, `select`, `reprice` and `critic` all made real
calls and returned schema-valid structured output; `match` worked on the second pass.

**Four agents failed every attempt**, silently falling back to the deterministic implementation:

```
tools.0.custom.input_schema.type: Input should be 'object'   (HTTP 400)
```

`tools[0]` is not one of ours — `AGENT_TOOLS` only names tools for the dry-run model, and the
real model binds none. It is the tool LangChain synthesises to implement
`withStructuredOutput`, whose `input_schema` is the JSON Schema of whatever Zod type the node
passed. The Anthropic API requires that schema's `type` to be `"object"`. These four pass a
top-level array:

| agent | schema passed to `decide()` | JSON Schema `type` | result |
|---|---|---|---|
| `planQueries` | `z.array(SearchQuerySchema)` | `array` | 400, fallback |
| `search` | `z.array(SearchQuerySchema)` | `array` | 400, fallback |
| `verify` | `z.array(VerifiedOptionSchema)` | `array` | 400, fallback |
| `supervisor` | `z.array(ItineraryCombinationSchema)` | `array` | 400, fallback |
| `match` | `z.record(z.array(RankedOptionSchema))` | `object` | worked on pass 2 |
| the other five | object schemas | `object` | worked |

The rule is exact: **every agent whose structured-output schema is a top-level array is
unreachable over the LLM path**, and no agent whose schema is an object failed for this reason.

### Why nothing surfaced it

The same three properties that hid `top_p: -1`, unchanged:

1. `decide()` catches non-schema errors and calls the deterministic fallback.
2. The fallback produces a *good* plan, so the output looks correct.
3. Every test drives a stub, so the real `input_schema` is never sent to a real API.

The only visible symptom is in the usage summary — `toolCalls: 0` and four agents marked
`fallback` — which nothing was asserting on.

### The fix

Wrap each array schema in a single-key object envelope and unwrap after validation, e.g.

```ts
// planQueries / search
const Envelope = z.object({ queries: z.array(SearchQuerySchema) });
// …decide(deps, "search", Envelope, user, () => ({ queries: fallback() }))
//   then take .queries
```

`match` already demonstrates that an object-typed wrapper is accepted, so this needs no provider
workaround. A regression test should assert that every schema handed to `decide()` produces a
JSON Schema with `type: "object"` — that check is static, needs no API key, and would have
caught this in CI.

**Not applied in this change.** It touches four nodes plus their fallbacks and deserves its own
change with its own tests, rather than being folded into a data-pipeline branch.
